How to read this

Tenancy spine is drawn once

Every business table carries firm_id, and every table below the company carries client_id too. Postgres row-level security (FORCED) filters on those two columns. To keep the diagrams readable those 42 tenancy arrows are omitted; each table's dictionary card lists them under Relationships → tenancy.

"Client" in the schema = "Company" in the UI

The table is still called client (it predates the naming decision); the screens say Company. Same thing.

Header / line pattern

claim → claim_line and ap_invoice → ap_invoice_line work the way OINV/INV1 do in SAP B1: the header carries the lifecycle and totals, the lines carry the amounts, coding and carbon snapshot.

Crow's-foot notation

||--o{ one → zero-or-many, parent required · |o--o{ parent optional (nullable FK) · |o--o| one-to-one, both optional · dotted .. = logical link with no physical foreign key (polymorphic or versioned reference).

Column chips

PK primary key · FK → table foreign key · unique unique on its own or within its parent · legacy kept for old rows, no longer written — do not build on it. ✓ in Req. means NOT NULL.

Identifiers & money

All primary keys are uuid (gen_random_uuid()). Money is numeric(14,2), rates numeric(18,6), never float. Timestamps are timestamptz.

Tenancy, users & masters

A firm (the accounting practice) owns companies and users. Partners and managers see every company; approvers and viewers see only the companies in user_client_grant. Claimants are the company's employees — they submit claims but never log in. Vehicles, FX rates and settings are per company.

Expense claims

One claim header owns many claim_line rows (one per receipt or mileage trip). A line is classified to a category, which decides GL code and whether the line goes to CarbonNext. An optional event groups claims from several people (a trip, a training). The approval_matrix_rule rows decide who may approve which amount band.

Design rules the schema enforces

These are the integrity rules that live in the database itself, not only in application code. They are deliberately not configurable per company.

  • Separation of duties in the database

    ck_claim_sod — the user who keyed a claim cannot approve it. ck_ap_invoice_sod — the approver of a vendor bill cannot be its filer, coder or submitter. ck_erpsync_entry_sod — the reviewer cannot be the editor. The service layer adds payer ≠ maker and the approval-matrix band check on top.

  • Idempotency everywhere something is created

    uq_claim_no, uq_claim_ingestion_job (a retried upload can never make a second claim), uq_release_batch_client_hash (content-addressed release), uq_entry_idempotency, uq_carbon_handoff_idem, uq_ap_invoice_idem, uq_erpsync_entry_line, uq_document_intake_job_sha.

  • Snapshots, not live lookups

    claim_line.carbon_relevant / carbon_class, ap_invoice_line.carbon_relevant, carbon_handoff.category_name / cost_centre / department are copied at classify or release time. Changing a category later never rewrites history.

  • Append-only, corrections by reversal

    audit_event rows chain prev_hash → hash, so tampering is detectable. A released line is never edited: a carbon_handoff row with direction = reversal backs out the earlier forward.

  • Logical links without a physical FK

    emission_entry.source_id and audit_event.entity_id are polymorphic (the *_type column says which table). emission_entry.factor_key + factor_version pins a specific emission_factor version. claim.ingestion_job_id and document_intake.ingestion_job_id point at ingestion_job without a constraint so the worker can run across tenants.

  • Money and currency

    A line keeps the document currency and total_amount, a human-verified fx_rate, and base_amount in MYR. Claim totals sum base_amount. If nobody entered a rate, exchange_rate for that month is used; if none exists the line is flagged rather than guessed.

  • Row-level security

    Every table except firm (the root) and emission_factor (global reference data) is filtered by firm_id / client_id GUCs. ingestion_job and document_intake carry an extra worker policy so the background worker can claim jobs.

  • Legacy columns on the claim header

    claim.vendor … tco2e and claim.category_id are the original one-receipt-per-claim fields. They moved to claim_line and are kept only for old rows; they are marked legacy in the dictionary and slated for removal.
